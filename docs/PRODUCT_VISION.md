# 洞察织机（InsightLoom）产品形态蓝图

> 本文档描述洞察织机（InsightLoom）的完整产品形态、分层架构、用户旅程与里程碑规划。
> 状态标注:✅ 已建成 · 🔜 规划中 · 💡 远期设想

## 一句话定位

**自托管的个人知识中枢:知识的"进、治、存、查、用"全闭环,数据永远是你的。**

- **进**:任意来源的内容随手丢进收件箱
- **治**:一队看得见的 Agent 蒸馏、互链、对抗审查,馆长(你)审批
- **存**:纯 Markdown 落盘,零锁定
- **查**:本地语义检索 + RAG 问答
- **用**:每日简报、知识图谱、持续巡库

### 各层要点

| 层 | 职责 | 关键设计 |
|---|---|---|
| ① 采集 | 把"收藏"的动作成本降到一次点击 | 全部进统一收件箱,不区分来源 |
| ② 治理 | 入库前蒸馏,保证进库质量 | Agent 只提案不落盘;对抗审查;人工审批三道闸 |
| ③ 存储 | 知识本体只是文件 | SQLite 只存过程状态;用户随时带着文件走 |
| ④ 检索 | 语义查得出、问得出 | 嵌入与索引全部本地,离线可用 |
| ⑤ 界面 | 每天的使用面足够薄 | 审批 2 分钟/天;简报 1 分钟/天 |

## 用户的一天(产品成熟后)

| 时刻 | 场景 | 背后发生什么 |
|---|---|---|
| 白天·随手 | 刷到好文章 → 点浏览器插件 / 转发给 TG bot | 进收件箱,流水线自动开工 |
| 晚上·2 分钟 | 打开审批台,像馆长一样批量点头/否决 | 蒸馏笔记落盘 vault,自动进向量索引 |
| 随时·查 | "我库里关于 RAG 重排是怎么记的?" | 语义检索 + RAG 回答,附引用笔记 |
| 每天早上 | 看简报:昨天进了什么、园丁发现几座孤岛 | 巡库报告 + 双链提案待审批 |
| 每周 | 知识图谱生长,孤岛减少 | 园丁持续织网 |

## 差异化(为什么这是产品而不是工具拼盘)

1. **闭环**:市面工具要么只做采集(Pocket/Readwise)、要么只做检索(khoj/各类 RAG)、要么只做笔记(Obsidian)。洞察织机把采集→治理→存储→检索串成一条流水线。
2. **治理是灵魂**:RAG 解决"查得到",Obsidian 解决"存得住",没人解决"进来的到底是什么质量"。洞察织机的 5-Agent 蒸馏 + 人工审批是唯一动治理层的产品。
3. **信任设计**:审批制(写)、纯 Markdown(存)、本地向量库(查)、任意模型(算)——"数据是你的"是架构事实,不是隐私承诺。

## 与"独立 RAG 项目"的关系(设计立场)

不单独立 RAG 项目线。理由:治理层(②)与检索层(④)是同一条知识流水线的上下游——没有治理的 RAG 是"垃圾进垃圾出",没有检索的治理是"只进不出"。两者合一,才是完整的第二大脑;分开则是两个半成品。
